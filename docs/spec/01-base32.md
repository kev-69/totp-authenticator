# Stage 1 — Base32 (RFC 4648 §6)

## Why Base32 at all?
A TOTP secret is raw bytes (RFC 4226 §4 R6: at least 128 bits, 160 recommended).
People sometimes have to type it by hand ("can't scan the QR? enter this key"),
so it needs a text form that:
- has no confusable characters: no `0`/`O`, `1`/`I`/`L`, `8`/`B`;
- is case-insensitive;
- survives URLs (`otpauth://...?secret=`) without escaping.

Base64 fails all three. Base32 uses `A–Z` + `2–7`: 32 symbols = 5 bits each.

## The core idea: 5 bytes ↔ 8 characters
lcm(8, 5) = 40 bits, so every **5 input bytes** become exactly **8 output characters**.

```
bytes:  [ 8 ][ 8 ][ 8 ][ 8 ][ 8 ]            = 40 bits
chars:  [5][5][5][5][5][5][5][5]             = 40 bits
```

When the input isn't a multiple of 5 bytes, the last group is partial:

| leftover bytes | bits | chars emitted | zero bits added | `=` padding |
|---|---|---|---|---|
| 1 | 8  | 2 (10 bits) | 2 | 6 |
| 2 | 16 | 4 (20 bits) | 4 | 4 |
| 3 | 24 | 5 (25 bits) | 1 | 3 |
| 4 | 32 | 7 (35 bits) | 3 | 1 |

Consequences the decoder must enforce:
1. **Only some lengths are possible.** An unpadded length `n` has `n mod 8 ∈ {0,2,4,5,7}`.
   Lengths with remainder 1, 3 or 6 can't come from any byte string, so they're typos or truncation.
2. **The zero bits really are zero.** §3.5 ("Canonical Encoding"): the pad bits must be zero, and
   decoders MAY reject input where they aren't. If we don't, `MY` and `MZ` both decode to `"f"`.
3. **Padding only appears at the end**, and the padded total is a multiple of 8.

## Test vectors (RFC 4648 §10)
```
""        → ""
"f"       → "MY======"
"fo"      → "MZXQ===="
"foo"     → "MZXW6==="
"foob"    → "MZXW6YQ="
"fooba"   → "MZXW6YTB"
"foobar"  → "MZXW6YTBOI======"
```

## What authenticator apps expect
Google's Key URI format says the `secret` parameter is Base32 **without padding**.
In practice users also type keys in lowercase, with spaces (`jbsw y3dp ...`).
Decision: `decode` is **case-insensitive** and **padding is optional**, but otherwise strict.
Removing spaces and dashes is a separate `normalize()` step for human-typed input,
so the core decoder never guesses.

## API
```ts
encode(data: Uint8Array, { padding = true }): string
decode(text: string): Uint8Array   // throws Base32Error
normalize(text: string): string    // strip whitespace/dashes, uppercase
```

## Security notes
- **A lax decoder is a key-handling bug, not just a formatting bug.** If `decode("A")` quietly returns
  zero bytes, HMAC gets an **empty key** and every code becomes predictable. Rejecting bad input here is
  the first defence. Stage 2 adds a minimum key length on top.
- **Error messages must not echo the input.** Errors get logged, and the input is a secret. Report
  the *position* of a bad character, never the character or the string.

## Naive version findings
The first version (`replace(/=+$/, "")` + `indexOf` + shift loop) passed **all 7 RFC vectors and the
round-trip property**, and still failed 18 of 44 tests. Lesson: test vectors show the happy path works;
they say nothing about what a decoder *accepts*.

| input | naive output | problem |
|---|---|---|
| `A` | *(empty)* | impossible length → **empty HMAC key** |
| `MY` / `MZ` | `66` / `66` | two strings, one key (non-canonical) |
| `MZ0W6YTB` | `66ff6f6261` | `indexOf("0") = -1`, and `-1` is all ones → typo becomes `0xff` |
| `MZ!W6YTB` | `66ff6f6261` | same bug: any junk becomes `0xff` |

fast-check's canonical property ("whatever decode accepts re-encodes to itself") found the first
counterexample (`"A"`) on its **first** run.

Fixes: a lookup table (invalid → -1, checked explicitly), a length-remainder check, a trailing-zero-bits
check, structured padding validation, and error messages that report positions, never input.
